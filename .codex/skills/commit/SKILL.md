# Git Commit 助手

## 核心理念

好的 commit message 回答两个问题：**做了什么** 和 **为什么这样做**。本技能确保每次提交都遵循统一规范，让项目历史可读、可追溯、可回溯。

## 执行流程

### 第 1 步：检查状态

执行以下检查：

```bash
git status          # 查看工作区状态
git diff --cached   # 查看暂存区变更（如果暂存区为空，询问是否要 git add）
git diff            # 查看未暂存变更
```

如果暂存区为空：
- 提示用户当前没有暂存的文件
- 列出有变更的文件，询问是否需要 `git add`
- 等用户确认后再继续

### 第 2 步：分析变更

仔细阅读 diff 内容，理解变更的性质和目的：

- **改了什么文件？** — 每个文件的变更类型（新增/修改/删除/重命名）
- **改了什么内容？** — 核心改动点（函数、章节、配置、文档等）
- **为什么要改？** — 从代码注释、关联 issue、上下文推断改动原因

### 第 3 步：参考历史风格

查看最近 10 条非合并 commit 的主题行，了解项目当前的命名习惯：

```bash
git log --oneline --no-merges -10
```

从历史 commit 中提取：
- 常用的 scope 关键词（如 `reader`、`webnovel`）
- 常用的 type 前缀
- 中文/英文的使用场景

### 第 4 步：生成 Commit Message

按以下格式生成 commit message，**先展示给用户确认，不要直接提交**。

#### 格式模板

```
<type>(<scope>): <中文简述>

<变更摘要>：用中文说明做了什么、为什么这样做

变更文件：
- <文件路径>：<该文件的变更说明>
- <文件路径>：<该文件的变更说明>
```

#### Type 类型选择

| type | 适用场景 |
|------|---------|
| `feat` | 新章节、新功能、新组件 |
| `fix` | 修复问题、调整内容、补充细节 |
| `docs` | 纯文档更新（大纲、台账、README） |
| `refactor` | 重构代码，不改变外部行为 |
| `chore` | 工具配置、依赖更新、脚本 |
| `style` | 格式调整（空格、换行，不影响逻辑） |

**选择原则**：
- 章节创作/新增功能 → `feat`
- 修改已有内容/修 bug/调整数据 → `fix`
- 只改文档/台账 → `docs`
- 只改配置/工具 → `chore`

#### Scope 作用域选择

| scope | 适用场景 |
|-------|---------|
| `webnovel` | 章节正文、大纲、人物设定、伏笔台账等网文创作内容 |
| `reader` | 阅读器前端代码 |
| `ledger` | 台账类文件（记忆台账、人物关系台账等） |
| `ci` | CI/CD 配置 |
| 留空 | 跨模块改动，或无法归入上述 scope |

**选择原则**：
- 优先使用已有 scope
- 跨多个 scope 的改动，选影响最大的那个
- 纯项目级配置改动可以不用 scope

#### 主题行（第一行）规范

- **用中文**描述核心改动（代码类改动可适当中英混合）
- **控制长度**：50 字以内（中文约 25 个汉字）
- **动词开头**：新增/修复/调整/重构/更新/清理/补充
- **聚焦「做了什么」**，不要写「修改了一些文件」这种空泛描述
- 章节类：`feat(webnovel): 新增第025章-暗流`
- 修复类：`fix(webnovel): 清理第024章禁用词`
- 重构类：`refactor(reader): 分页器改为进度驱动动画`

#### 正文规范

正文**必须**包含两个部分：

1. **变更摘要**（2-5 句话）：用中文讲清楚做了什么、为什么这样做
   - 先说目的/背景，再说具体改动
   - 多文件改动时，概括共同主题
   - 如果改动的理由在 diff 中不明显，一定要写出来

2. **变更文件列表**：每个变更文件一行
   - 用 `- <路径>：<说明>` 格式
   - 说明该文件的具体改动，不要只写「修改」
   - 如果改动很小（如只改了一行），可以合并说明

### 第 5 步：用户确认后提交

展示生成的 commit message 后，**等待用户确认**。

用户确认后执行：

```bash
git commit -m "<主题行>" -m "<正文>"
```

**不要**：
- 不要跳过确认直接提交
- 不要添加 `-a` 提交未暂存的文件（除非用户明确要求）
- 不要修改用户不相关的文件

提交成功后，展示 commit hash 和简短摘要。

## 特殊场景处理

### 场景 1：只有文档/台账变更

如果变更只涉及 `.md` 文件（台账、大纲等），scope 用对应的类别，type 通常用 `docs`。但如果台账变更是伴随章节创作的副作用，则跟随章节的 type。

### 场景 2：多文件跨模块变更

当变更跨越多个模块时：
- 主题行概括核心目的
- 正文中按模块分组说明
- scope 选影响最大的模块

### 场景 3：WIP（进行中）的提交

如果变更是中间状态，用户明确只是想保存进度：
- type 用 `wip`（work in progress）
- 主题行写清楚当前进度
- 正文说明接下来要做什么

### 场景 4：紧急修复

如果是修 bug/改错误：
- type 用 `fix`
- 主题行点明修复了什么
- 正文必须说明问题原因和修复方式

## 项目约定速查

基于项目历史 commit 总结的约定：

- **章节类**：`feat(webnovel): 新增第XXX章-章节标题` 或 `feat(webnovel): 第XXX章-章节标题 完成`
- **修复类**：`fix(webnovel): <具体修复内容>` 或 `fix(reader): <具体修复内容>`
- **台账类**：`docs(ledger): <台账更新说明>`
- **字数扩充**：`fix(webnovel): 扩充第XXX章字数`
- **禁用词替换**：`fix(webnovel): 清理禁用词`
- **重构类**：`refactor(reader): <重构说明>`

## 反例 — 这些不要做

- ❌ 主题行超过 50 字 → 拆分到正文
- ❌ 没有 type 前缀 → 必须加 `type:` 或 `type(scope):`
- ❌ 正文为空 → 至少写变更文件列表
- ❌ 用「修改」「更新」这种空泛动词 → 写具体做了什么
- ❌ 英文主题行（除非纯技术改动，如 CI 配置）→ 网文创作内容用中文
- ❌ Merge commit 当普通 commit → merge 保留原样
- ❌ 多个不相关的改动塞进一个 commit → 提示用户拆分提交
